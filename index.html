기획 배경

팀원 중 뮤지컬에 관심 있는 분이 있었고, 당시 인터파크 같은 단순 티켓 예매 사이트는 있었지만 뮤지컬·연극 배우 지망생을 위한 인프라는 빈약했습니다. 공간 대여, 오디션 공지, 커뮤니티 등 지망생에게 필요한 기능과, 예술을 좋아하는 일반인을 위한 티켓 예매·VOD·굿즈 구매를 한 곳에서 해결할 수 있는 통합 플랫폼이 부족하다는 걸 확인했습니다.

팀원 6명이 직접 시장 조사와 도메인 검색을 통해 이 니즈를 검증했고, 예술가 지망생과 예술 애호가 두 타겟을 모두 아우르는 통합 플랫폼으로 ShowU를 기획했습니다.

서비스 소개

예술가 지망생과 팬을 연결하는 통합 플랫폼. 공연 티켓 예매·공간 대여·굿즈/경매·VOD·커뮤니티 6개 도메인이 하나의 결제 흐름으로 연결된 구조로, k6 동시 200명 부하테스트로 Race Condition과 결제 위변조를 직접 재현하고 해결했습니다.

DB 레벨 Unique Index → 애플리케이션 레벨 트랜잭션 → Toss 서버사이드 검증으로 이어지는 3단계 방어 구조로 데이터 정합성과 결제 보안을 완성했습니다.

마주친 기술적 문제 ▼
1. 동시 예약 요청으로 인한 중복 예약 (Race Condition)
개선 전 흐름 (Race Condition 발생) — 시퀀스 다이어그램
개선 후 흐름 (트랜잭션으로 차단) — 시퀀스 다이어그램
문제 원인
  • 티켓 예매/공간 대여 도메인에서 동시 요청 시 같은 좌석·시간대에 중복 예약이 발생했습니다.
  • find() → 확인 → save() 사이의 간격에서 여러 요청이 동시에 통과하는 Race Condition이 원인이었으며, seatSchema에 Unique Index가 없어 DB 레벨에서도 차단이 불가능한 구조였습니다.
  • k6 부하테스트(동시 200명)로 재현한 결과 중복 예약 9건이 발생했으며, 같은 좌석에 여러 명이 입장하는 심각한 비즈니스 문제로 이어질 수 있었습니다.
해결 과정
  • DB 레벨 방어로 seatSchema에 { showId, date, time, seatNumbers } 복합 Unique Index를 추가했습니다.
  • 애플리케이션 레벨 방어로 mongoose.startSession()으로 트랜잭션을 시작하고 find()와 save() 모두 동일 세션 안에서 처리했습니다.
  • 트랜잭션 충돌 시 발생하는 WriteConflict(code: 112)를 catch에서 잡아 500 대신 400으로 반환해 클라이언트에 명확한 오류 메시지를 전달했습니다.
session.startTransaction().session(session)commitTransactionabortTransactionerror.code === 11000WriteConflict
결과
  • k6 부하테스트(동시 200명) 기준, 중복 예약이 9건 → 0건으로 완전히 해결됐습니다.
  • 트랜잭션 적용으로 평균 응답시간이 315ms → 1,100ms로 증가했지만, 티켓 예매 도메인 특성상 성능보다 데이터 정합성을 우선해 트레이드오프를 감수했습니다.
  • 좌석 예약뿐 아니라 공간 대여 도메인에도 동일하게 적용해 서비스 전반의 중복 예약 문제를 해결했습니다.

2. 예약·결제 컬렉션 분리로 인한 데이터 불일치 (부분 저장)
트랜잭션 원자성 보장 — 시퀀스 다이어그램
문제 원인
  • 티켓 예매는 Seat(좌석 예약)와 TicketPayment(결제 정보), 공간 대여는 Rental(대여 예약)과 RentalPayment(결제 정보)가 각각 별도 컬렉션에 저장되는 구조였습니다.
  • 예약 저장 성공 후 결제 정보 저장 단계에서 오류가 발생하면, 예약 데이터만 남고 결제 정보가 저장되지 않는 부분 저장 상태가 발생했습니다.
  • 예약은 완료됐지만 결제 정보가 없는 데이터 불일치가 생겨, 관리자가 수동으로 정합성을 맞춰야 하는 운영 리스크가 있었습니다.
해결 과정
  • mongoose.startSession()으로 트랜잭션 세션을 시작하고, 예약과 결제 정보 저장 모두 동일 세션 안에서 처리했습니다.
  • 두 저장 작업을 하나의 트랜잭션으로 묶어 어느 한 쪽이 실패하면 abortTransaction()으로 전체를 롤백하도록 구성했습니다.
  • Race Condition 해결에서 적용한 트랜잭션 구조를 공간 대여 도메인에 동일하게 확장 적용해 서비스 전반의 데이터 정합성을 보장했습니다.
mongoose.startSession().session(session)commitTransactionabortTransactionwithTransaction
결과
  • 예약 저장 성공 + 결제 정보 저장 실패 시나리오에서 예약이 자동 롤백되어 부분 저장 케이스가 완전히 제거됐습니다.
  • 수동 정합성 작업 없이 예약·결제 데이터가 항상 일치하는 구조가 됐습니다.
  • Race Condition 해결(DB 레벨 Unique Index) → 트랜잭션 원자성 보장(애플리케이션 레벨)으로 이어지는 2단계 데이터 정합성 방어 구조를 완성했습니다.
3. 결제 금액 클라이언트 위변조 가능성
결제 검증 흐름 — 시퀀스 다이어그램
문제 원인
  • 프론트엔드에서 Toss 결제 완료 후 paymentKey를 generateRandomString()으로 직접 생성해 백엔드로 전달하는 구조였습니다.
  • 백엔드가 Toss 서버에 실제 결제 검증을 요청하지 않고 클라이언트가 보낸 값을 그대로 신뢰해 DB에 저장했습니다.
  • 브라우저 개발자 도구로 amount 값을 조작한 요청이 그대로 통과할 수 있는 결제 위변조 리스크가 존재했습니다.
해결 과정
  • requestPayment() 이후 handlePaymentSuccess()를 직접 호출하던 구조를 제거하고, Toss가 실제 paymentKey를 successUrl에 자동으로 부착해 리다이렉트하는 흐름으로 수정했습니다.
  • 백엔드에서 Toss Payments 서버사이드 검증 API(/v1/payments/confirm)를 직접 호출해 실제 결제금액과 요청금액의 일치 여부를 확인했습니다.
  • 검증 통과 후에만 DB에 결제 정보를 저장하는 순서를 보장했으며, 티켓/공간/경매/굿즈 4개 도메인 결제 전체에 동일하게 적용했습니다.
/v1/payments/confirmpaymentKeyorderIdamount 검증서버사이드 검증successUrl 리다이렉트

  • Postman으로 금액 조작 요청(실제 결제금액 340,000원 → 요청 1,000원)을 직접 재현한 결과, Toss 서버사이드 검증 단계에서 FORBIDDEN_REQUEST(403) 반환으로 차단됐습니다.
  • 클라이언트에서 금액을 조작한 요청이 DB에 저장되지 않고 서버 레벨에서 완전히 차단되는 구조가 확인됐습니다.

기획 배경

🔴 외부 LLM API(OpenAI 등) — 문서 데이터가 외부 서버로 전송되어 기업·의료·법무 등 민감한 도메인에서 프라이버시 문제 발생. API 비용도 지속 발생.

✅ PrivateGPT — 5개월간의 LangChain/RAG/NLP 학습을 바탕으로, 9개 챗봇 프로젝트 중 외부 API 호출 없이 완전 로컬에서 동작하는 프라이버시 보장 RAG 챗봇을 포트폴리오 대표 프로젝트로 선정했습니다.

서비스 소개

업로드한 문서에 대해 질문할 수 있는 로컬 기반 RAG 챗봇. 임베딩 모델과 LLM 모두 로컬(Ollama, 임베딩은 nomic-embed-text / LLM은 Mistral)에서 실행되어 외부 API 호출 없이 동작하며, 민감한 문서도 안전하게 처리할 수 있는 프라이빗 AI 시스템.

OpenAI API를 사용하면 문서 데이터가 외부 서버로 전송되어 프라이버시 문제가 발생하고 API 호출 비용도 발생합니다. 임베딩과 LLM 모두 로컬에서 실행하는 Ollama(임베딩: nomic-embed-text, LLM: Mistral) 조합을 선택해 "Private"GPT라는 이름처럼 데이터가 외부로 나가지 않는 구조를 구현했습니다.

담당 역할

RAG 파이프라인 설계(문서 로딩→청킹→임베딩→벡터 검색→답변 생성), 임베딩 캐싱 구조 구현, 대화 히스토리 체인 연결, Streamlit UI 구현

1. 동일 문서 재업로드 시 임베딩 재생성 문제
RAG 파이프라인 전체 흐름 — 아키텍처 다이어그램
문제 원인
  • 사용자가 동일한 파일을 다시 업로드하거나 페이지를 새로고침할 때마다 임베딩을 처음부터 재생성했습니다.
  • 초기 구조에서는 LLM인 Mistral(7B)을 임베딩에도 함께 사용했습니다. 임베딩 전용 모델이 아니다 보니 청크 4개를 임베딩하는 데 약 118초가 걸렸고, 새로고침이나 재업로드마다 이 시간이 그대로 반복됐습니다.
  • 문서가 많아질수록 대기 시간이 선형적으로 증가하는 구조였습니다.
해결 과정
  • 임베딩을 전용 모델로 분리했습니다. nomic-embed-text(137M)로 교체하자 같은 작업이 118.27초 → 2.24초로 줄었습니다. LLM과 임베딩 모델의 역할이 다르다는 것을 수치로 확인한 지점입니다.

3. 관련성 없는 문서도 무조건 검색 결과에 포함되는 문제
문제 원인
  • 기본 as_retriever() 설정은 관련성 점수와 무관하게 무조건 상위 k개 문서를 반환합니다.
  • 문서와 전혀 관련 없는 질문("오늘 저녁 뭐 먹을까?")에도 가장 유사한 청크 4개를 반환해, LLM이 엉뚱한 컨텍스트로 답변을 생성하거나 할루시네이션이 발생했습니다.
해결 과정
  • search_type="similarity_score_threshold"를 적용해 관련성 점수가 기준값 이하인 문서는 검색 결과에서 제외했습니다.
  • threshold 값을 정하기 위해 관련 질문과 무관한 질문의 점수 분포를 직접 측정했습니다. 관련 질문이 0.44~0.50, 무관한 질문이 0.40~0.56으로 구간이 겹쳤고, 무관한 질문이 더 높은 점수를 받는 경우도 있었습니다.
  • nomic-embed-text는 무관한 텍스트끼리도 코사인 0.7 근처를 주는 모델이라 점수가 좁은 대역에 몰려 있습니다. OpenAI 기준값(0.7~0.9)을 적용하면 관련 문서까지 전부 탈락해, 실측 분포에 맞춰 threshold를 0.05로 설정했습니다.
# 개선 전: 관련성 무관하게 무조건 4개 반환
retriever = vectorstore.as_retriever()

# 개선 후: 관련성 점수 기준 이하 문서 제외
retriever = vectorstore.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.05, "k": 4}
)
similarity_score_thresholdscore_threshold: 0.05as_retriever()
결과
  • 문서와 무관한 질문("오늘 저녁 뭐 먹을까?")에 "모른다"고 응답하는 것을 확인했습니다. 이는 threshold 단독이 아니라 프롬프트 제약("주어진 context만 사용, 모르는 경우 모른다고 답변")과 함께 동작한 결과입니다.
  • 점수 분포를 측정한 결과, 이 임베딩 모델에서는 threshold 하나로 관련/무관을 분리할 수 없다는 것을 수치로 확인했습니다. 어떤 값을 잡아도 관련 문서가 탈락하거나 무관한 문서가 통과합니다.

기획 배경

제1회 K.I.T. 바이브코딩 공모전(506팀)에서 교육 현장의 페인포인트를 해결하는 서비스를 개발하게 됐습니다. 팀원 중 지인인 은퇴한 초등학교 교사에게 직접 인터뷰한 결과, 학년 담임 선생님 전체가 한자리에 모여 생활기록부를 보며 반배정을 수작업으로 조합하는데 하루 종일 걸린다는 것을 확인했습니다.

성적·성격·성향·특이사항(미술 특기생, 학급 반장 등) 등 복합 조건을 동시에 처리해야 하는 문제에 알고리즘과 LLM API(공모전 필수 요건)를 병렬 실행하는 하이브리드 구조로 접근했습니다. LLM 장애 시 알고리즘 결과로 즉시 폴백해 서비스 연속성을 보장합니다.

서비스 소개

교육기관의 수작업 팀/반 배정을 AI로 자동화한 웹 서비스. 교사가 학생 명단 CSV를 업로드하면 AI와 최적화 알고리즘이 성적·성격·성향·특이사항 등 복합 조건을 종합해 균형 잡힌 팀/반 구성을 자동 배정합니다.

자연어 AI 도우미("성적 균형 맞춰줘")로 배정 결과를 실시간 조정하고, 팀별 균형 점수와 분석 대시보드로 배정 결과를 시각화합니다.

담당 역할

서비스 기획 총괄 — 은퇴 초등학교 교사 인터뷰로 문제를 검증하고 서비스 기획. 벨빈(Belbin) 팀역할론 개념을 참고해 섀넌 엔트로피 기반으로 성격 유형 분포 다양성을 측정하는 방식과 제약 기반 힐클라이밍 최적화를 결합한 4단계 하이브리드 알고리즘 설계. 로컬 알고리즘과 Claude Sonnet 4 API 병렬 실행 구조 및 균형 점수 가중치(성적 30% / 성격 26% / 성향 26% / 성별 10% / 나이 4% / 인원 4% 가중 로그 곱연산) 설계. CLAUDE.md / AGENTS.md 기반 AI 코딩 컨벤션 정립.

문제 원인
  • 공모전 일정에 맞춰 기능을 반복 배포해야 했으나 GitHub Actions 기록 기준 총 86회 중 26회 배포가 실패했습니다 (성공률 약 70%).
  • Secrets 설정 오류(이메일 주소 입력), Dockerfile 파일명 오타(Dokcerfile), 보안 그룹 SSH 포트 차단, Docker 권한 미설정 등 오류 원인이 매번 달라 장애 감지와 대응에 수 분이 걸렸습니다.

  • --no-cache 옵션과 fetch-depth: 0을 표준화해 캐시 충돌과 코드 미반영 문제를 원천 차단했습니다.

2. 배포 exit 0인데 서비스는 구버전 — Silent Failure
EBS 볼륨 확장 전/후 (EC2 인스턴스) — 구성도
문제 원인
  • 파이프라인은 정상 완료(exit 0)되는데 실제 서비스는 계속 구버전 코드로 동작했습니다.
  • 에러 로그 없이 구버전이 유지되는 Silent Failure였기 때문에 원인 파악에 시간이 걸렸습니다.
  • docker pull 실행 시 no space left on device 에러가 조용히 발생하고 있었고, docker images 명령으로 확인하니 반복 배포로 누적된 이미지 4개(각 ~1GB)가 7.6GB EBS 볼륨을 가득 채운 상태였습니다.
  • 새 이미지를 pull할 공간이 없어 EC2가 기존 이미지를 그대로 재사용하고 있었던 것이었습니다.
해결 과정
  • docker images 명령으로 누적 이미지 목록을 확인해 원인을 특정했습니다.
  • AWS 콘솔에서 EBS 볼륨을 7.6GB → 30GB로 확장했습니다.
  • growpart /dev/nvme0n1 1 + resize2fs /dev/nvme0n1p1로 파티션·파일시스템을 무중단 리사이즈했습니다.
  • 불필요한 기존 이미지를 삭제(docker image prune)해 공간을 확보하고, 워크플로우에 --no-cache 옵션을 표준화해 레이어 누적 자체를 방지하는 구조를 잡았습니다.

결과
  • docker pull이 정상화되어 이후 배포 = 서비스 반영이 일치하게 됐습니다.
  • docker ps, docker logs를 활용한 배포 후 검증 절차를 정립해 동일 유형의 Silent Failure 재발을 방지했습니다.
3. 단일 방식으로는 복합 조건의 균형 배정이 불가능
알고리즘 + Claude API 병렬 실행 → 균형 점수 비교 → 최적 결과 선택 — 플로우
문제 원인
  • 교육기관의 팀/반 배정은 성적, 역할 분배, 성격·성향, 특이사항(장애·ADHD 등) 등 복합 조건을 동시에 고려해야 합니다.
  • 알고리즘 단독으로는 자유 텍스트 특이사항 같은 비정형 조건을 처리하기 어려웠습니다.
  • Claude API 단독으로는 응답 일관성과 속도 문제가 있었으며, API 장애 시 서비스가 중단되는 리스크도 있었습니다.
해결 과정
  • 벨빈(Belbin) 팀역할론 개념을 참고해 섀넌 엔트로피 기반으로 성격 유형 분포 다양성을 측정하는 4단계 하이브리드 알고리즘과 Claude Sonnet 4 API를 병렬 실행했습니다.

기획 배경

🔴 Anthropic 공식 Memory MCP — JSON 파일 기반이라 여러 에이전트가 동시에 쓰면 파일이 손상될 수 있음. 동시 접근 제어 없음.

🔴 유사 프로젝트 (mnehmos/synch-mcp 등) — 락 관리는 있으나, 충돌 발생 시 어떤 값을 채택할지 결정하는 충돌 해결 전략이 MCP 도구 레벨에서 분리되어 있지 않음.

✅ Nexus MCP — ShowU에서 Race Condition(중복 예약 9건 → 0건)을 해결한 경험을 AI 에이전트 환경에 적용해, 동시 접근 제어와 충돌 해결 전략을 명확히 분리한 경량 MCP 서버를 만들게 됐습니다.

서비스 소개

여러 AI 에이전트가 동일한 공유 메모리 키에 동시 접근할 때 발생하는 충돌을 해결하는 MCP(Model Context Protocol) 서버. Python MCP SDK의 FastMCP 위에서 동작하며, 핵심 로직(locks.py / conflicts.py / memory.py)은 MCP SDK에 의존하지 않는 순수 Python으로 분리해 단위 테스트만으로도 검증 가능하게 설계했습니다.

acquire_lock으로 선점권을 확보하면 다른 에이전트의 쓰기를 막을 수 있고, 락을 쓰지 않는 경로에서는 resolve_conflict가 버전을 비교해 충돌을 처리합니다. 자주 경합하는 자원은 락으로 직렬화하고, 경합이 드문 자원은 락 없이 쓰되 충돌 시에만 전략으로 해결하는 이중 구조입니다. renew_lock으로 heartbeat을 유지해 Zombie Lock을 방지하며, 충돌 시에는 last_write_wins / first_write_wins / merge 전략으로 자동 병합합니다. 공유 메모리 상태는 SQLite WAL로 영속화되어 서버 재시작 후에도 100% 복구됩니다. ShowU 프로젝트에서 MongoDB 트랜잭션으로 Race Condition(동시 예약 중복 9건 → 0건)을 해결한 경험을 AI 에이전트 환경에 적용했습니다.

현재 구조는 MCP 서버 단일 인스턴스를 전제로 합니다. 락이 threading.Lock 기반이라 프로세스 내 스레드 간 배타성만 보장하며, 여러 인스턴스로 확장하려면 Redis 등 외부 저장소 기반 락으로 교체해야 합니다.

담당 역할

MCP 서버 설계 및 구현 — SQLite WAL 모드 기반 공유 메모리 설계. acquire_lock / release_lock / renew_lock / resolve_conflict 4개 도구 구현. Zombie Lock 방지 heartbeat 패턴, 재시작 후 상태 복구, 충돌 해소 전략(last_write_wins / first_write_wins / merge) 구현.

테스트 및 검증 — pytest 21개 테스트 작성 (locks / memory / concurrent 3개 파일). MCP Inspector(localhost:6274)에서 stdio 프로토콜로 실제 도구 호출 검증.

AI 코딩 컨벤션 문서화 — CLAUDE.md / AGENTS.md 작성. 에이전트가 코드베이스 구조·설계 원칙·테스트 규칙을 즉시 파악할 수 있도록 정리.

1. 동시 부하에서 seq 기반 순서 판정의 결정론 실증
time.time() 동률(tie) 발생 → seq 기반 결정론 — 개선 전/후 비교 다이어그램
문제 원인
  • itertools.count() 기반 seq로 순서 판정을 설계했지만, 단위 테스트는 단일 스레드 시나리오만 다루고 있었습니다.
  • 락도, 충돌 해결도 결국 여러 에이전트가 동시에 요청하는 시나리오를 위한 기능인데, 실제 수십~수백 개 스레드가 동시에 경쟁하는 부하 조건에서도 seq 판정이 무너지지 않는지는 부하 테스트로 실증된 적이 없었습니다.
해결 과정
  • tests/test_concurrent.py를 concurrent.futures.ThreadPoolExecutor로 신규 작성했습니다.
  • test_concurrent_lock_exclusivity: 50개 스레드가 동일 resource_id에 동시 acquire_lock 시도 → 성공이 정확히 1건인지 검증.
  • test_concurrent_resolve_deterministic: 100개 스레드가 의도적으로 stale한 expected_version으로 동시 쓰기 → 최종값이 항상 가장 높은 seq를 가진 쓰기와 일치하는지 1000회 반복 검증.
  • test_concurrent_no_data_corruption: acquire_lock → resolve_conflict → release_lock 패턴으로 50개 스레드 순차 쓰기 → 최종 version == 50, 손실 0건 검증.
ThreadPoolExecutor50~100 스레드 동시 부하1000회 반복 결정론 검증seq 기반 순서 판정
결과
  • time.time()이 아닌 seq를 쓴 이유(Windows ~15ms 해상도 한계)가 이론이 아니라 실제 부하 조건에서 수치로 증명됐습니다.

2. 에이전트 크래시 시 Zombie Lock으로 인한 블로킹
Zombie Lock 발생 → heartbeat 패턴으로 해결 — 개선 전/후 타임라인 다이어그램
문제 원인
  • acquire_lock은 TTL이 지나야 자동 해제됩니다. 에이전트가 락을 쥔 채로 예기치 않게 종료되면(크래시, 네트워크 단절 등) 다른 에이전트는 원래 설정된 TTL이 끝날 때까지 무조건 블로킹됩니다.
  • TTL을 길게 잡으면 크래시 시 블로킹 시간이 길어지고, 짧게 잡으면 정상적으로 오래 걸리는 작업도 중간에 락을 잃습니다 — 둘 다 좋은 선택지가 아닌 구조였습니다.
해결 과정
  • LockManager에 renew(resource_id, agent_id, lock_token, ttl_seconds) 메서드를 추가해 heartbeat 패턴을 지원했습니다.
  • 짧은 TTL(예: 5초)로 락을 잡고, 작업 중 주기적으로 renew를 호출해 TTL을 계속 연장합니다. 에이전트가 살아있는 동안은 락이 끊기지 않고, 크래시로 heartbeat이 멈추면 그 즉시 원래의 짧은 TTL만큼만 기다리면 됩니다.
  • server.py에는 동일한 dict 반환 패턴({"success": false, "error": ...})을 지키는 renew_lock MCP 도구를 추가했습니다.
renew_lockheartbeat 패턴짧은 TTL + 주기적 갱신Zombie Lock 방지
결과
  • 작업 시간을 예측할 필요 없이, "살아있다는 신호"만으로 락 유지 여부를 결정하는 구조로 바뀌었습니다.

3. 서버 재시작 시 공유 메모리 상태 완전 손실
dict → SQLite WAL 영속화 전환 — 아키텍처 다이어그램
문제 원인
  • SharedMemoryStore는 순수 Python dict로 상태를 들고 있었습니다. MCP 서버(stdio 프로세스)가 재시작되면 그동안 쌓인 모든 버전 정보, 충돌 해결 기록이 통째로 사라졌습니다.
  • 여러 에이전트가 장시간 협업하는 운영 환경에서는 재시작 한 번으로 모든 공유 상태가 초기화되는 건 치명적입니다.
해결 과정
  • SharedMemoryStore를 SQLite 기반으로 재설계했습니다. db_path 파라미터를 받아 기본값은 기존 테스트 하위 호환을 위해 :memory:로 유지하고, 연결 직후 PRAGMA journal_mode=WAL을 설정합니다.
  • entries / conflict_history 테이블에 value를 JSON으로 직렬화해 저장하고, propose()의 충돌 판정 로직(seq 비교 포함)은 그대로 유지한 채 저장소만 dict → SQLite로 교체했습니다.
  • 읽기(get / conflict_history)는 별도 커넥션 + 별도 락으로 분리해 WAL의 이점(쓰기 중에도 읽기가 블로킹되지 않음)을 살렸습니다. 실 운영에서 server.py의 SharedMemoryStore()도 db_path="nexus_memory.db"로 변경했습니다.
SQLite WALPRAGMA journal_mode=WALdb_path=":memory:" 하위 호환재시작 후 100% 복구
결과
  • :memory: 기본값 덕분에 테스트는 여전히 빠르고 격리되어 있고, 실제 서버만 파일 기반으로 전환되어 재시작에도 살아남습니다.
